## Experiment

### SteamVR / ALVR Runtime Diagnostics

**Purpose**

Identify the source of the unstable SteamVR / ALVR connection and establish a reproducible VR runtime environment for Quest 2 teleoperation.

**Setup**

- Oculus Quest 2
- Linux workstation
- SteamVR
- ALVR
- OpenVR
- Python VR teleoperation environment

**Test**

- Restarted SteamVR and ALVR after terminating existing VR-related processes
- Checked active SteamVR / ALVR processes
- Tested different SteamVR runtime versions
- Tested SteamVR rollback
- Repeated ALVR connection attempts
- Checked whether stale runtime processes remained after SteamVR termination
- Investigated possible ALVR port conflicts

**Result**

Several different runtime failures were reproduced depending on the SteamVR / ALVR configuration.

Observed errors included:

- SteamVR Error 303
- SteamVR Error 307
- SteamVR Error 108
- ALVR:
  - `Address already in use (os error 98)`

Rolling back SteamVR changed the failure mode but did not fully solve the VR runtime problem.

The results suggested that the primary instability was related to the SteamVR / ALVR runtime configuration rather than only the Python or robosuite code.

A completely stable SteamVR / ALVR configuration was not established during this session.

## Issues

- SteamVR / ALVR connection is not yet stable
- Multiple SteamVR error states were observed
- ALVR port conflict may exist
- Previous VR processes may remain alive after failed sessions
- Runtime restart procedure needs to be made reproducible
- Quest 2 tracking cannot be reliably tested until the runtime environment is stable
